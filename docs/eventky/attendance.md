# Native event attendance

An RSVP is an ordinary Pubky post with exact kind `attendance`. Its envelope `parent` is the event's normal Pubky post URI. The existing post controller supplies author identity, native post ID, local-first persistence and homeserver publication. The records retain native post identity and social compatibility; event discussion hides attendance-kind status cards and presents current responses in a dedicated attendee section.

The string content holds `schema: "eventky.attendance"`, `schema_version: 1`, the event's `event_uid`, RFC 5545 `partstat` (`ACCEPTED`, `TENTATIVE`, or `DECLINED`), and an ISO UTC `dtstamp`. An optional `recurrence_id` uses the same date/time representation as the event's recurrence identity. No email address, claimed attendee identity or organizer authority is accepted in the payload. An absent response means no decision has been published; the UI does not synthesize a public `NEEDS-ACTION` reply.

Only source posts whose author, URI, parent and event UID agree participate in resolution. The latest native post ID per author and scope wins, independently of response timestamps supplied in content. An occurrence-specific decision overrides that author's series decision even if the series decision was published later. A response to another occurrence never changes the selected occurrence. Nonrecurring calendar cards use the same series/default scope as their canonical post page.

Changing a response creates a new native reply; previous replies remain normal social records, without appearing as event discussion comments. Deleting a response removes it from indexed discovery after Nexus catches up, so an older remaining response can become effective again. There is no organizer-written attendee roster or delegation protocol. These responses express public intent, not verified admission or capacity reservations.

The UI obtains indexed attendance replies from Nexus through controller → application → service. Nexus reply streams reject kind filters, so discovery fetches all event replies and selects attendance records after hydration. Discovery requests pages of 50, scans at most 1,000 raw replies per request and explicitly reports partial results on missing records, repeated pages or a cap. A valid continuation exposes another bounded scan; status-only pages do not imply an empty complete discussion. Counts describe the available index, not an atomic snapshot across concurrent edits or proof that every homeserver write has been indexed. A fetch failure shows an unavailable state rather than zero authoritative attendees. Successful writes update the current mounted view immediately; other clients observe them after indexing and refresh.

While the attendance component remains mounted, an uncertain write retains its prepared post and exact payload, scoped to account, event and recurrence identity. This is not a durable draft across reloads. Retrying the same response uses that identity; another response is blocked until the uncertain write is resolved. The hook rechecks the signed-in account after asynchronous preparation before publication. Cancelled events and signed-out users cannot use RSVP controls.

## Native attendee and discussion surfaces

The compact Attendees row shows Going/Maybe totals and up to five native avatar previews. View attendees opens the existing native dialog, grouped into Going, Maybe and Can't go. Each author appears once for the selected scope. Declined responses appear inside the dialog; roster rows link to native profiles. Groups initially render at most 50 people, with an explicit expansion action. Response controls identify Whole event, Whole series or This occurrence; occurrence overrides and public-response semantics remain unchanged.

The event discussion keeps the existing quick reply and native reply shell, filtering attendance records and muted authors after raw pagination and hydration. The event comment badge reports the filtered count only when discovery is complete; partial discovery omits a misleading exact number and retains loading, continuation or retry affordances. Ordinary post discussions retain their existing path. Counts remain index-derived rather than atomic across concurrent writes.

Concurrent readers share fetch and hydration work by backend, viewer, parent event and raw cursor. Full post batches use the existing native post/file/user hydration application boundary. Indexed sources take precedence over ordinary cached copies. Pending event reply creates and edits keep their optimistic content until the indexed post envelope matches, including attachments, parent and embedded content. This pending registry is in-memory and does not survive a reload; local deletion tombstones remain authoritative locally.
