# Public calendar subscriptions

The sidecar serves `GET /v1/calendar.ics?calendar=<encoded-normal-post-URI>` and HEAD. The app exposes the same feed at `/api/eventky/calendar.ics?calendar=<encoded-normal-post-URI>`. The proxy chooses `EVENTKY_PROJECTION_URL` from server configuration, sends no browser credentials, rejects redirects, and accepts only one canonical calendar post URI. `webcal:` can be used by the UI as a launch affordance for the public HTTPS URL.

The subscription represents the current calendar within the configured Nexus inventory. It includes complete VEVENT masters and same-UID original-instance exceptions, without limiting them to an occurrence-view date range. Membership is derived from each event's `calendar_uris` and actual author against the current calendar owner/contributors/exclusions. Native deletion removes the source; no historical or last-known-good payload is served. Still-published CANCELLED events and exceptions remain until their author changes or deletes them. There is no separate cancellation archive or hidden source retention. Subscribers need a published cancellation before native deletion if their calendar client requires an explicit cancellation notice.

Anonymous feeds use the configured Nexus public moderation policy. They cannot apply a subscriber's private mutes or local personal reminders. Calendar inventory staging is never published. Pending invalidations, incomplete inventory, stale source checks beyond 60 seconds, unavailable/invalid records anywhere in inventory, unsupported recurrence/timezone serialization, duplicate UIDs or export limits cause HTTP 503 with Retry-After. A missing calendar after a complete current read returns 404. No successful feed is truncated. Coverage is relative to the configured Nexus, not the entire Pubky network.

Limits: at most 5,000 inventory sources and 8 MiB current content in the atomic feed snapshot; at most 500 calendar series and 2 MiB selected source content/output. The shared contract's per-event payload, recurrence and timezone limits also apply. Active subscription recurrence rules use the documented contract expansion profile; source definitions that cannot be safely serialized produce 503. Occurrence API ranges are separately limited to 93 days, matching the shared engine. This does not constrain the series included in subscriptions.

Recurrence queries and subscription exports execute in dedicated Node workers using immutable snapshots. Default concurrency is two, configurable to one with `EVENTKY_WORKERS=1`; at most eight additional requests may wait for one second. Each active job has a two-second deadline including startup and response serialization. A timed-out worker is terminated and retains its concurrency slot until exit. Client disconnects and shutdown cancel queued and active work. The main HTTP thread loads at most 5,000 sources / 8 MiB of body content only after checking indexed counts and UTF-8 byte totals in one read transaction; queued work holds no source snapshot. Derived database schema v1 migrates once to v2 to populate the byte-count index. Statistics above the source-count cap are bounded lower bounds, and coverage reports the limit. Inventory staging enforces the same global count/byte budgets before promotion; an oversized inventory remains incomplete and its partial staging is never served.

Each worker has a 128 MiB V8 old-generation limit, 16 MiB young-generation limit, and 4 MiB stack limit. These are JavaScript heap limits, not total process RSS limits: Node excludes native allocations and ArrayBuffers. Node process heap flags (including `NODE_OPTIONS=--max-old-space-size=...`) override worker limits, so startup rejects these flags and each worker verifies its actual V8 heap ceiling before work. Deploy the process with a container memory limit (the initial VPS configuration uses 512 MiB); bounded cloned inputs and output add to heap overhead. The result envelope is bounded to 4 MiB plus 16 KiB to accommodate JSON escaping of the 2 MiB feed. On the query/feed request path, the main thread only performs bounded SQLite reads and request/result handling; an unavailable filesystem or saturated host can still delay that work. [Node worker resource-limit documentation](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#new-workerfilename-options).

Overload, timeout, worker failure, stale source coverage, or incomplete recurrence expansion returns HTTP 503 without a partial successful response. Revision/checkpoint/pending changes and freshness are checked again against the live store after worker completion. A cursor whose source changes while its worker runs returns 409 so the client restarts pagination. Workers receive no environment secrets and perform no network or database IO. These limits affect derived calendar views and subscriptions; ordinary Pubky post feeds remain available through Nexus.

ETag hashes the exact emitted bytes. Last-Modified uses the persisted projection revision timestamp, including deletions. If-None-Match takes precedence over If-Modified-Since. Current coverage is checked before returning 304, so a stale projection cannot extend the life of an old cached success. Date-only validation is conservative for subsecond modifications; ETags are the reliable validator. All successful responses require revalidation, while failures are no-store. HEAD returns equivalent metadata without a body.

The fixed-origin Next proxy validates content type, completeness headers, ETag/date shape, UTF-8 and calendar framing, bounds streamed bytes to 2 MiB, and copies only a small response-header allowlist. Unexpected HTTP diagnostics remain internal; public failure text is static. No URLs found inside source calendar content are fetched.

Run focused checks with `npx vitest run --config services/eventky-projection/vitest.config.mts`. The HTTP fixture binds only a random loopback port. Build using `npm run eventky:projection:build`; both `server.cjs` and `worker.cjs` must be deployed together. Tests compile the production worker entry and cover dense recurrence, heap exhaustion, a hung worker, queue overflow/expiry, source changes during conditional requests, snapshot limits, and legacy-store migration.
